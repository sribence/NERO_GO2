# audio (port 9107)

Event-reactive sound playback. Runs fine in a headless container with no
audio hardware — playback is attempted via a pluggable backend, but the
HTTP response and JSONL log always tell you what actually happened.

## Env vars

| Var | Default | Meaning |
|---|---|---|
| `REDIS_HOST` / `REDIS_PORT` | `redis` / `6379` | event bus |
| `PROXIMITY_COOLDOWN_S` | `5` | min seconds between auto-triggered `proximity_warning` plays |

## Event -> sound mapping

Defined in `app.py` as `SOUND_LIBRARY`:

| event_name | file |
|---|---|
| `proximity_warning` | `sounds/proximity_warning.wav` |
| `task_complete` | `sounds/task_complete.wav` |
| `test` | `sounds/test.wav` |

An unknown `event_name` falls back to `sounds/test.wav` (`DEFAULT_SOUND`)
and the response has `"fallback_used": true`.

### Adding a new sound

1. Drop a `.wav` file into `sounds/` (or generate one with
   `python _gen_sounds.py`, editing/adding a `make_beep(...)` call there).
2. Add an entry to `SOUND_LIBRARY` in `app.py`.

## Playback backends

Tried in order, first one available wins:
1. `simpleaudio` (Python package, cross-platform, no external process)
2. `aplay` (shelled out to, Linux/ALSA — present in most Debian-based
   containers with `alsa-utils` installed; not installed by default in
   this Dockerfile, so in a stock container `simpleaudio` is what
   actually plays)

If neither works (e.g. genuinely headless with no `simpleaudio` wheel
available), the endpoint still returns `"played": false, "backend":
"none"` — verifiable without real audio hardware — and logs the attempt.

## Endpoints

### `POST /audio/play/{event_name}`

```bash
curl -X POST http://localhost:9107/audio/play/task_complete
# => {"played": true, "backend": "simpleaudio", "file": "task_complete.wav",
#     "event": "task_complete", "fallback_used": false, "file_found": true}
```

### `GET /audio/library`

```bash
curl http://localhost:9107/audio/library
# => {"events": {...}, "default": "test.wav", "sounds_dir": "...",
#     "available_files": ["proximity_warning.wav", "task_complete.wav", "test.wav"]}
```

## Redis auto-trigger

Subscribes (background thread, auto-reconnects with backoff if Redis is
down) to `mc.core.proximity_alert`. Any message on that channel triggers
`play_event("proximity_warning")`, throttled to at most once per
`PROXIMITY_COOLDOWN_S` seconds so a burst of alerts doesn't spam the
speaker.

Test it manually:

```bash
redis-cli PUBLISH mc.core.proximity_alert '{"distance_m": 0.4}'
```

## Logging

Every play attempt (manual or auto-triggered) is appended to
`logs/events.jsonl`:

```json
{"t": 1234.5, "pillar": "audio", "level": "info", "msg": "play event 'task_complete' -> task_complete.wav (played=true, backend=simpleaudio)", "played": true, "backend": "simpleaudio", "file": "task_complete.wav", "event": "task_complete", "fallback_used": false, "file_found": true}
```

## Known limitations

- `simpleaudio.play()` is fire-and-forget (doesn't block the HTTP
  request on the sound's duration), so `/audio/play/...` returns as soon
  as playback *starts*, not when it finishes.
- No per-event volume control or mixing; one sound plays at a time per
  backend call, overlapping plays are left to the backend's own
  behavior.
- The 3 placeholder WAVs are plain sine-wave beeps generated by
  `_gen_sounds.py` (no external assets) — swap in real sound design
  later by just replacing the files under `sounds/`.
